# 블로그 표지 이미지 다양화 구현 계획

- 상태: 구현·검증 완료 · 기능 브랜치 반영 · 운영 배포 전
- 작성일: 2026-10-21
- 목적: [intent.md](intent.md)
- 구현 기준: [spec.md](spec.md)

승인 범위는 명세에 따른 생성기·관련 테스트 개선과 기존 자동 생성 표지 181개 교체다. [Change Approval](../../../AGENTS.md#change-approval)에 따라 사용자 구현 승인 후 아래 작업을 수행했다. 원문과 이미지 경로를 보존했다. 커밋·푸시는 별도 사용자 요청에 따라 `feat/blog-cover-diversity`에서 진행하며, 운영 배포는 수행하지 않는다.

## 1. 구현 접근

현재 로컬 SVG 생성기를 확장한다. 그림 카탈로그, 글의 주제 배정, 중복을 고려한 선택, 기존 파일 교체 절차를 분리하고 기존 글 저장·조회 방식에 연결한다.

1. 기존 181개 글·표지의 관계와 해시를 읽어 기준 목록을 만든다.
2. 글별 주제 배정과 대표 12개 장면을 작성하고 실제 카드 크기로 비교한다.
3. 24개 주제군의 장면을 확장하고, 같은 주제 안에서도 구도가 다른지 확인한다.
4. 장면 선택·배정 보존·중복 검사를 구현한다.
5. 기존 파일 교체 도구와 새 글 저장부를 연결한다.
6. 전체 dry-run과 미리보기에서 기준을 확인한 뒤 승인 범위의 표지를 적용한다.
7. 해시·브라우저·테스트·빌드를 확인하고 결과와 복원 위치를 남긴다.

## 3. 데이터와 생성기 연결

### 3.1 읽기 기준

- 기존 글은 `gray-matter`로 읽고 공개 기준인 `region: 서울`, `sourceType: 정보글`을 적용한다.
- 실제 제목·정규화한 날짜·태그·슬러그·`sourceId`를 읽고, 주제 큐를 ID로 연결한다.
- `coverImage`가 비어 있는 글은 현재 `src/lib/posts.ts`와 같은 기본 경로 규칙을 적용한다.
- 기존 대체 텍스트와 그림이 맞는지도 확인한다. 서울타워를 명시한 야경 글은 해당 요소가 있는 장면을 지정한다.
- 초기 배정 순서는 정규화한 날짜 내림차순, 날짜가 같으면 글 ID 순으로 고정한다. 디렉터리 열거 순서에 의존하지 않는다.

### 3.2 배정 정보

내부 배정은 `topicId`, `subjectId`, `sceneId`, `paletteId`, `catalogVersion`, `reason`, `reviewRequired`를 사용한다. 의미 있는 추가 구도가 있다면 `compositionId`도 기록한다. 같은 장면의 색상·좌우 반전·크기 변화로 구도 ID를 늘리지 않는다.

생성된 SVG에는 생성기·버전·주제·장면·배색을 식별하는 `data-cover-*` 속성을 기록한다. 새 글 생성은 기존 SVG에서 배정을 읽어 사용량을 집계한다. 공개 메타데이터에는 그림 식별자만 포함하고 검토 메모나 백업 경로는 넣지 않는다.

글별 배정 근거는 정적 주제 배정표에, dry-run·예외·해시·복원 정보는 임시 보고서에 남긴다. 새 글을 만들 때마다 소스 코드의 배정표를 자동 수정하거나 별도의 운영 JSON 파일을 추가하지 않는다.

### 3.3 기존 호출과 호환

- `createBlogCoverSvg(topic)`의 기존 단일 인자 호출을 유지한다. 확정된 배정을 전달할 때만 선택 옵션을 사용한다.
- 순수 SVG 렌더링과 파일 조회·중복 선택을 분리해, 렌더링 함수가 임의의 파일을 쓰지 않게 한다.
- `ensureTopicCoverAsset(topic, options)`는 기존 `publicDir` 옵션과 `{ coverImage, coverAlt }` 반환 형식을 유지한다.
- 글 저장부는 파싱된 실제 제목을 우선해 표지 생성기에 전달한다. 이미 조회한 기존 글 정보도 선택에 사용할 수 있게 전달한다.
- 새 글의 표지 생성·조회는 현재 호출 흐름 안에서 처리한다. 기존 글의 재생성을 일일 생성 경로에 넣지 않는다.
- 후보가 소진되면 반환 형식을 바꾸지 않고 경고·검토 결과를 남긴다. 실제 저장 실패는 정상 생성으로 보고하지 않는다.

## 5. 교체 도구의 실행 계약

다음 옵션을 구현했다. 기본 실행은 공개 파일을 변경하지 않는 dry-run이다.

| 모드·옵션 | 동작 |
| --- | --- |
| 기본값 또는 `--dry-run` | 기존 파일을 읽고 임시 폴더에 예상 결과·변경 목록·미리보기 작성 |
| `--report-dir` | 임시 보고서 위치 지정. `public/`와 보호할 원본 경로 안은 허용하지 않음 |
| `--apply --manifest` | 검토한 목록의 원본 해시를 재확인하고 명시된 대상만 백업·교체 |
| `--restore --manifest` | 해당 적용의 백업만 복원. 이후 수정된 파일은 보존하고 충돌 보고 |

모드는 함께 실행하지 않는다. 검증 실패·충돌·저장 실패는 0이 아닌 종료 코드와 실패 항목을 남긴다. 적용 모드에서 dry-run 결과와 다른 대상을 조용히 추가하지 않는다.

| 프로젝트 | 테스트·린트·빌드 및 결과 보고 | AC-09 |

브라우저에서는 데스크톱 폭 1280px와 모바일 390px·320px를 확인한다. 홈 추천 글, 블로그 최신 12개, 다른 주제의 중간 구간, 상세 16:9를 보고 주요 사물 잘림·가로 넘침·깨진 이미지·제목 중복을 확인한다. 실제 로컬 서버의 SVG 응답도 확인해 별도 미리보기만 바뀐 상태를 완료로 판단하지 않는다.

빌드 전 생성 데이터의 상태를 기록한다. 검색 인덱스 등 이번 업무와 무관한 생성 파일의 변경은 분리하고 보존·복원 여부를 확인한다. 빌드 산출물에는 비밀값·내부 도구 폴더·원본 세부 데이터가 섞이지 않는지 기존 보안 기준으로 확인한다.
