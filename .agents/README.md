# Agent Workflow Index

이 폴더는 에이전트 전용 작업 워크플로우와 공통 규칙을 보관합니다. 사용자/팀이 보는 제품 문서는 `docs/`에 두고, 에이전트가 반복해서 쓰는 프롬프트와 검토 절차는 `.agents/workflow/`에 둡니다.

## Rule Routing

`AGENTS.md`의 `Rule Loading`을 적용한다. 단순 조회는 관련 지침만 선택하며, 후속 작성·테스트·Git 규칙을 미리 읽지 않는다. 이 저장소에는 별도 번호형 라우터나 추측 제한·최소 작업·작업 분리·레거시·코드 marker 전용 규칙이 없다. 별도로 적용되는 지침과 대상 코드의 보호 표시는 해당 판단·변경 전에 확인한다.

보안 판단·설계 또는 문서/코드 변경에는 [SECURITY_RULES.md](rules/SECURITY_RULES.md)의 공통 기준인 1·7절을 적용한다. 아래에서 해당하는 절과 마지막 체크리스트의 관련 항목만 추가한다. 절별 선택은 읽는 범위이며, 현재 행위에 적용되는 보안 의무를 생략하는 근거가 아니다.

| 현재 행위·대상 | 추가 보안 기준 |
| --- | --- |
| 외부 데이터·AI 입력의 수집, 저장, 검증, 테스트 fixture | 2절 |
| Markdown·HTML·외부 URL 렌더링 | 3절 |
| API 설계·구현·검증 | 4절 |
| CI/CD·권한·자동 커밋·배포 | 5절; 배포 산출물 확인은 8절도 적용 |
| 의존성 추가·업데이트·보안 경고 | 6절 |
| 문서·블로그 작성·수정 | 8절의 문서 공개 점검 항목 |
| 빌드 후 산출물 확인 | 8절 |

테스트 보완은 검증 대상에 해당하는 절을 선택한다. 로그 분석은 비밀값·개인정보 확인에 1·7절을 적용하고, 원인·실패 경계에 따라 추가한다. 확정된 계획 기록만으로 구현·실행 규칙을 추가하지 않으며, 아래 워크플로우는 PRD→SRS 변환·검토를 실제 수행할 때 선택한다. spec 작성에는 현재 요구사항과 내용에 맞는 보안 기준을 적용한다.

## Task Flow

| 입력 | 기본 흐름 |
| --- | --- |
| 외부 요구사항 | 요구사항 확인 → PRD → SRS → tasks → 구현·검증 |
| 내 아이디어 | intent.md → spec.md → plan.md → 구현·검증 |

### intent → spec → plan의 원리

의도, 필요한 동작, 구현 방법을 차례로 구체화한다. 각 단계는 앞 단계의 결과를 입력으로 사용하고, 다음 단계가 판단할 수 있는 기준을 남긴다. 구현 방법을 먼저 정해 원래 목적이나 요구사항을 바꾸지 않는다.

| 단계 | 답할 질문과 정리할 내용 | 다음 단계로 넘길 기준 |
| --- | --- | --- |
| `intent.md` | 왜 필요한가: 문제, 대상 사용자, 기대 결과, 범위·제약, 미확정 사항 | 명세를 작성할 수 있게 의도와 제약을 정리하고, 모르는 점을 구분했다 |
| `spec.md` | 무엇이 충족되어야 하는가: 동작, 사용자 흐름, 데이터·인터페이스, 제외 범위, 수용 기준 | 요구사항이 intent와 연결되고 검증 가능하며, 구현을 막는 모호함·정책 충돌을 해소했다 |
| `plan.md` | 어떻게 구현하고 확인할 것인가: 변경 파일, 작업 순서·의존 관계, 위험, 검증 방법 | 각 작업과 완료 확인 방법이 spec에 연결되고, 현재 작업·승인 범위 안에 있다 |
| 구현·검증 | 계획에 따른 변경과 요구사항을 확인하는 검사 수행 | 수행한 검사와 결과, 미검증 사항·남은 한계를 제시할 수 있다 |

- 아이디어 경로의 문서는 `docs/works/<작업명>/` 아래에 두며, 전체 업무 현황과 남은 작업 요약은 [docs/works/README.md](../docs/works/README.md)에 연결한다.
- 아이디어 경로의 `tasks`는 `plan.md` 안의 실행 체크리스트로 표현할 수 있다. 별도 `tasks.md`를 필수로 만들지 않는다.
- 구현·검증 중 요구사항 변경이 필요하면 spec을, 목적·제약이 바뀌면 intent부터 정리하고 관련 계획을 맞춘다. 구현상의 이유로 범위나 권한을 조용히 확대하지 않는다.
- 리뷰·배포·운영 피드백은 해당 행위가 현재 승인 범위에 있을 때 진행한다. 운영에서 발견한 문제는 다음 intent의 입력이 될 수 있으며, 자동 커밋·배포나 상시 실행을 뜻하지 않는다.

### 입력과 산출물 선택

- 외부 요구사항 경로에서 PRD는 대상 사용자, 제품 범위·제외 범위와 성공 기준을, SRS는 구현할 동작과 검증 가능한 요구사항을 정리한다. `tasks`는 작업 단위, 순서·의존 관계와 완료 확인 방법을 정리한다.
- 모호한 외부 요청은 intent 수준의 확인을 먼저 한다. 구체화된 아이디어는 이미 확보한 의도·요구사항을 재사용하고, 아직 필요한 spec 또는 plan 단계부터 진행할 수 있다.
- 제공받은 PRD/SRS는 해당 단계의 입력으로 활용한다. 기존 문서가 spec 역할을 충족하면 재사용하며, 같은 요구사항을 새 파일에 중복 작성하지 않는다. 제품 범위·요구사항 변경은 기존 프로젝트의 PRD/SRS 갱신 조건을 따른다.
- 단순 조회는 관련 정보 확인으로 마친다. 작은 수정은 대화의 의도·작업 체크리스트와 필요한 검증으로 처리할 수 있다. 위 파일명은 역할을 설명하며, 별도 파일 생성·보관은 `AGENTS.md`의 조건을 따른다.
- 현재 단계의 판단·행위에 필요한 지침만 선택한다. PRD→SRS를 실제 변환·검토할 때 아래 해당 워크플로우를 적용하며, 단계 이름만으로 문서 생성·커밋·외부 작업을 실행하지 않는다.

## Rules

- `docs/prd/*_prd.md`: 제품 요구사항 문서
- `docs/srs/*_srs.md`: 소프트웨어 요구사항 명세 산출물
- [docs/works/README.md](../docs/works/README.md) (`docs/works/<작업명>/`): 아이디어·개선 작업(`intent.md`, `spec.md`, `plan.md`) 현황 및 체크리스트
- `.agents/workflow/*_prompt.md`: 에이전트 전용 워크플로우
- `.agents/rules/*_RULES.md`: 프로젝트 공통 규칙
- `.omo/`와 `.antigravitycli/`는 도구/세션 메타데이터이므로 source-of-truth로 사용하지 않습니다.
